# ADR 0004: Record verified PyPI distribution without implying runtime deployment

**Status:** Accepted
**Date:** 2026-10-07
**Supersedes:** None

## Context

The repository's release architecture already separates deterministic release qualification, retained
package bytes, GitHub Actions OIDC/Sigstore provenance, GitHub Release publication, and PyPI Trusted
Publishing. ADR 0002 established the OIDC-only PyPI authority split, and ADR 0003 corrected the
bot-created GitHub Release handoff without turning the dispatch event into release evidence.

After those decisions were accepted, `v0.1.0` was actually published. The retained-byte GitHub
Release was created from qualified CI artifacts, and the downstream PyPI workflow successfully
reverified the published release assets and provenance before publishing the exact wheel and sdist
through PyPI Trusted Publishing with GitHub OIDC. PyPI publish attestations were generated by the
pinned PyPA publisher.

The root README and `RELEASE_PROVENANCE.md` still contained pre-publication wording that described
PyPI activation/publication as only conditional. The documentation also did not state clearly that
this repository distributes a Python package rather than deploying a hosted runtime service.

## Decision

Update the public documentation to record the verified publication state while preserving the
existing release authority boundaries.

The repository will describe its production distribution surface as:

1. operator-selected version preparation and protected acceptance into `main`;
2. operator-selected existing version tag plus exact qualified main-branch CI run;
3. automated retained-byte GitHub Release publication after deterministic evidence/provenance
   reverification; and
4. automated PyPI Trusted Publishing, using GitHub OIDC, only after the published GitHub Release is
   independently reverified by trusted default-branch code.

The successful `v0.1.0` PyPI publication is historical external evidence that this path executed
successfully. It does not make workflow configuration itself proof that a future publication
succeeded.

The repository will also state explicitly that no cloud, Kubernetes, VM, container-service, website,
or other hosted application/runtime deployment workflow is configured. The GitHub environment
`pypi` is an OIDC publication authority boundary, not a runtime deployment target.

## Consequences

Users can discover the published package directly from the README and install it from PyPI without
first cloning the repository. Operators can find the release/provenance contract, GitHub Releases,
PyPI project, compatibility/deprecation policy, and the implemented CLI surface from the primary
navigation.

Release documentation must distinguish three different facts:

- a repository workflow is configured;
- a particular GitHub Release or PyPI publication actually succeeded; and
- a hosted application/runtime was deployed.

Those facts are not interchangeable.

Future releases remain deliberately operator-gated at version/tag/qualified-run selection. This
decision does not authorize automation to choose semantic versions or create release tags on its own.

## Assurance impact

The documentation now reflects the externally observed successful `v0.1.0` publication rather than
leaving a stale precondition-only claim. The evidence chain remains non-compensatory: PyPI
publication cannot repair missing release qualification, retained evidence, package binding, or
provenance verification.

The PyPI publication authority remains isolated to the final job with `id-token: write`; the
release publisher still has no PyPI OIDC authority, and the verifier still has no OIDC authority.
Hashes remain integrity identities rather than authentication. GitHub Release asset provenance and
PyPI publish attestations remain separate from trial-evidence authority and do not retroactively
authenticate unrelated historical evidence.

## Non-claims

- A successful PyPI publication does not prove that a hosted application/runtime has been deployed.
- The GitHub Release database object is not claimed to be separately cryptographically signed.
- PyPI publish attestations authenticate the package publication path they cover; they are not human
  maintainer signatures or proof of agent/provider behavior.
- The successful `v0.1.0` publication does not guarantee that a future publication will succeed.
- Repository documentation does not replace verification of the actual GitHub Release, PyPI project,
  workflow run, or retained provenance when those facts are assurance-relevant.
